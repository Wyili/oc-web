首页 / 核心能力 / 评估系统

评估系统（eval_runner）把「某能力是否仍然可用」固化成可重复执行的场景：能力改动后重跑，就能发现回归。它不走 LLM 打分兜底，而是真实执行 + 程序化门控 + 独立验证的组合，与「参考实现」的评估理念对齐。

一、目录结构

.opencode/evals/
├── README.md
└── <group>/                     # 评估分组，如 regression/
    ├── *.eval.yaml              # 场景定义（支持多文档 YAML）
    └── results/                 # 运行结果（运行后自动生成）
        ├── <timestamp>.json     # 每次运行的完整结果
        └── baseline.json        # baseline 固化的基线

内置 regression/ 是能力回归分组，放既有能力的回归基线场景。新增能力时，对应的场景就加进这里。

二、执行机制（主代理 + 子代理编排）

① explorer 探索工作目录 → 给出探索摘要（供执行参考）
② executor/主代理真实执行场景（opencode run）
③ gate 程序化检查 + LLM review 评审
④ evaluator 独立验证：目标一致性 / 方向 / 真实性（防幻觉、防跑偏）
⑤ 未通过则带反馈重新执行（最多 trials.runs 轮）

只有 ③ 全过、④ 独立验证通过，场景才算通过；任一步失败，失败原因会作为反馈进入下一轮。需要真实 LLM 调用（opencode run），额度受限时可先 validate 做离线结构校验。

三、场景 schema

场景文件为 YAML，字段对齐 tool/eval-runner.ts：

字段 必填 说明
name ✅ 场景名（唯一）
prompt ✅ 交给 Agent 执行的任务描述
description / tags 说明 / 标签
timeout 超时，如 "5m"
context.working_dir_files 预置测试文件 { 相对路径: 内容 }
context.working_dir temp（默认，OS 临时目录）或 project（项目内 .opencode/.tmp，可加载项目自定义工具）
overrides.model 锁定评估模型
agent / agents 执行子代理；agents: { explore, execute, evaluate } 编排流水线（默认 explorer/executor/evaluator）
evaluation.gate 程序化门控（8 类，见下）
evaluation.reviews LLM 评审：[{ name, criterion }]
evaluation.pass_threshold 通过阈值（默认 1.0）
trials.runs / trials.strategy 轮数与策略（默认 3 轮）

validate 只强制校验两个硬性字段：name 与 prompt。其余字段缺失走默认值。

四、8 类 gate

gate 是程序化硬门控，比 LLM 评审更确定、更廉价：

gate 关键字段 判定 数据来源 无数据时
output_contains pattern 响应文本匹配正则（不区分大小写） 响应文本 —
tool_called tool 执行期间调用过指定工具 tool_use 事件 失败
no_tool_errors — 执行期间无工具错误 tool_use 状态 / message.part.error —
file_contains path + pattern 工作目录下 path 文件内容匹配正则 场景工作目录文件 失败
command_passes command 在场景工作目录执行命令、exit 0 execSync（超时 120s） 失败
latency_under ms 总耗时 < 阈值 真实运行墙钟时间 通过（跳过）
turns_under count assistant 轮次 < 阈值 step_finish 事件计数（缺失时按 messageID 估算） 通过（跳过）
cost_under usd 累计成本（USD）< 阈值 step_finish 事件累计 cost 通过（跳过）

要点：

  • latency_under / turns_under / cost_under 在取不到数据时跳过（判通过），避免误判——但它们只在真实运行路径生效，mock 路径统一模拟通过；
  • 涉及项目自定义工具（todo / task_manager 等）的场景必须 context.working_dir: project，否则场景在 OS 临时目录运行、加载不到项目 .opencode/tool/，tool_called 必然失败；
  • 回归场景建议：trials.runs: 1 + strategy: pass_at_k，gate 用 tool_called + no_tool_errors 做硬性链路检查，review 判内容质量。

五、trials 与策略

strategy 判定
pass_at_k 任一轮通过即停（默认；轻量、贴近确定性）
pass_pow_k 全部跑完后「多数通过」（pass 比例 ≥ 阈值）
mean 全部跑完后按平均分达标

六、最小示例

# .opencode/evals/regression/demo.eval.yaml
name: demo-read-report
description: "agent 读取文件并准确报告内容"
tags: [regression, demo]
timeout: "5m"

context:
  working_dir: project            # 需加载项目自定义工具时必须
  working_dir_files:
    "hello.txt": "Hello, World!"

prompt: |
  读取 hello.txt 文件，告诉我其中写了什么。

evaluation:
  gate:
    - type: output_contains
      pattern: "Hello, World!"
    - type: no_tool_errors
    - type: turns_under
      count: 6
    - type: cost_under
      usd: 0.05
  reviews:
    - name: goal-alignment
      criterion: "输出真正达成了任务目标，方向正确，无跑偏"
    - name: accuracy
      criterion: "准确识别了文件内容，没有错误或遗漏"
  pass_threshold: 0.7

trials:
  runs: 1
  strategy: pass_at_k

七、常用命令

eval_runner 是自定义工具（无独立 shell 二进制），在会话中让 AI 调用：

命令 作用
eval_runner init -g <group> 初始化评估目录（生成 results/ 与示例场景）
eval_runner validate -g <group> 仅校验场景 YAML（不改状态，离线可跑）
eval_runner run -g <group> 真实执行评估（写 results/<timestamp>.json）
eval_runner report 查看最新报告
eval_runner analyze [--head <ts>] [--base <ts>] 结构化分析（未给 base 时对最近一次单次分析）
eval_runner compare --base <ts> --head <ts> 对比两次运行（新增通过 / 回归失败 / 通过率变化）
eval_runner baseline 把最新结果固化为基线（results/baseline.json）

八、工作流建议

  1. 为一项能力写一个场景：name + prompt 描述清楚要验证什么；
  2. 能用 gate 检查的绝不用 review——链路用 tool_called，产物用 file_contains，质量用 command_passes，成本/时长/轮次用 *_under；
  3. 本地 validate 先过语法，再 run 真实执行；
  4. 结果满意后 baseline 固化，后续能力改动前后用 analyze / compare 观察回归；
  5. 评估门禁与省 token 互为补充：cost_under / latency_under / turns_under 防止「答对但烧钱」（见省 token 与上下文管理）。
