首页 / 核心能力 / 工作流

把多步骤任务固化为可重复执行的 DAG。工作流用 YAML 描述，由内置 workflow_runner 工具加载执行——适合「每次都要按同样顺序做」的流程：提交流水线、例行检查、周报生成。

一、什么是工作流

一个工作流 = 一个 YAML 文件，定义在 .opencode/workflows/ 下，由 workflow_runner 加载：

inputs ──▶ [start] ──▶ [节点…] ──▶ [end] ──▶ outputs

关键特征：

  • DAG 结构：节点 + 边，执行顺序由拓扑排序决定，循环依赖会被拒绝；
  • 真实执行：code 跑脚本、http 发请求、llm 调模型、agent 多轮循环、tool 调外部命令；
  • 可传参：运行时传入 key=value，节点内用模板语法引用。

二、YAML 三要素

每个工作流由「元信息 + 节点 + 边」三部分组成：

部分 字段 说明
元信息 api_version / name / version / description name 必填，与文件名一致
运行接口 inputs / outputs / defaults 入参声明、输出映射、默认超时
节点 nodes[] 每个 { id, type, data }
边 edges[] 每个 { source, target, condition? }

最小骨架：

api_version: "1"
name: my-workflow
description: 工作流说明
defaults:
  timeout: 60

inputs:
  - key: name
    label: "姓名"
    type: string
    required: false
    default: "world"

nodes:
  - id: start
    type: start
    data:
      outputs:
        - key: name
          value: "{{inputs.name}}"
  - id: end
    type: end
    data:
      outputs:
        - key: greeting
          value: "{{variables.greeting}}"

edges:
  - source: start
    target: end

三、节点类型（12 种）

类型 作用 关键 data 字段
start 入口，初始化变量 outputs（key/value，可用 {{inputs.xxx}}）
code 执行脚本 language（python/bash）、script、timeout、export_var
condition 分支判断 mode: llm + prompt，或 expression；branches
llm 调用大模型 prompt、system_prompt、model、temperature、export_var
http 发 HTTP 请求 url、method、headers、body、export_var
template 加载模板文件插值后执行 template（相对工作流目录）、language
agent Agent 多轮循环（工具调用） prompt、max_turns（默认 3）、model
tool 执行外部命令/工具 tool_name、args、fail_on_error
foreach 循环迭代子图 iterable、loop_var、subgraph_nodes、concurrent
parallel 并行分支 branches / parallel_nodes
merge 合并并行/循环结果 source_vars
end 结束，汇总输出 outputs，配合顶层 outputs 映射

大多数节点支持 export_var（字符串或 {name, value_from} 列表）：脚本/接口返回 JSON 时按 key 提取为后续可用的 {{variables.xxx}}。

四、变量插值

节点字段（prompt / script / url / value 等）中可用 {{表达式}} 引用上下文：

表达式 含义
{{inputs.xxx}} 工作流入参
{{variables.xxx}} export_var 导出 / start 初始化的变量
{{node_id.output}} 指定节点输出（如 {{time_check.output.hour}}）
{{node.xxx}} 最近一次产生该 key 的节点输出
{{assets.xxx}} 资产变量（预留）

管道修饰（可选）：{{expr | default:'值'}}（空值回退）、{{expr | trim}}。

五、触发方式

工作流有两条入口——终端 CLI（不经过 LLM）与对话内工具调用：

# CLI
workflow_runner list                      # 列出全部工作流
workflow_runner validate <name>           # 校验
workflow_runner run <name> key=value      # 运行（可传输入参数）

# 对话中让 AI 调用 workflow_runner 工具
#   operation: list | validate | run

validate 会检查：缺少 name / nodes / edges、非 start 节点无入边、非 end 节点无出边、condition 缺 expression 或 prompt、http 缺 url、llm 缺 prompt、边引用不存在的节点、依赖环。

六、内置示例

工作流 说明 用到的节点
demo-greeting 自包含示例：问候 + 时间 + 条件分支 start / code / condition / llm / end
commit-flow 标准提交流水线：git diff --check 通过后 add + commit tool / condition / code
routine-check 例行健康检查：工作区脏就跑类型检查与测试 tool / condition / code
weekly-report 周报生成：统计本周提交并按类型分组，LLM 整理成 markdown code / llm
jira-submit-close 提审闭环：建单 → 提交暂存 → 编译 → 推送 → 关单 脚本见 scripts/
feishu-task 飞书任务联动 —

commit-flow 的分支结构（节选）：

nodes:
  - id: whitespace_check
    type: tool
    data: { tool_name: "git diff --check", timeout: 30 }
  - id: check_result
    type: condition
    data: { expression: "{{whitespace_check.output}} == ''" }
edges:
  - { source: check_result, condition: true,  target: do_commit }
  - { source: check_result, condition: false, target: fail_info }

七、校验与落地

  1. 先 validate 再 run——循环依赖、缺字段都在校验阶段暴露，别等执行到一半失败；
  2. 参数化而非硬编码——把仓库路径、周数、提交信息等做成 inputs；
  3. 节点名即依赖——edges 表达真实数据流向，condition 边实现分支；
  4. fail_on_error 慎用——false 表示失败也继续（适合「检查类」步骤），默认语义见节点文档；
  5. 对外部命令加 timeout——避免单个节点卡死整个工作流；
  6. llm 节点需要密钥——依赖工作流 LLM 密钥环境变量（团队网关密钥或 OPENAI_API_KEY，具体见工作流 README）；code 节点依赖 python3。

编排子代理与工作流的分工：工作流适合确定性、可重复的固定步骤；需要判断与探索的复杂任务更适合 子代理与编排。工作流里的 agent / llm 节点则把两者连起来。
