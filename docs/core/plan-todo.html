首页 / 核心能力 / 计划与 Todo

让 Agent「先想后做」，并让任务在跨会话之间不丢失锚点。本文对齐内部「参考实现」的计划引擎（规划-执行分离）与任务管理机制，并补齐 opencode 定制版的增强项。

一、先想后做：规划与执行分离

复杂任务最贵的错误是「方向错了还在埋头做」。计划机制把工作分成两个阶段：

planning（只读规划）  →  goal / approach / steps / verification
executing（按计划执行）→  逐步推进 + 每步验证

规划阶段不修改任何文件，只产出计划并等待确认；确认后才进入执行。这与 子代理与编排 的 Chain 模式天然契合：规划 → 实施 → 审查。

二、斜杠命令与 TUI 流程

命令 作用
/plan <目标> 进入计划模式（先分析再实施），禁止文件变更
/plan_checkout [路径] 加载已有计划文件并进入 plan 模式
/run 执行当前计划
/compact_run <计划> 先压缩上下文，再执行计划（上下文紧张时用）
/cancel 停止当前操作，报告进度与部分改动
/tasks 查看 / 管理后台任务
/todo 查看 / 创建 / 更新 todo
/context 查看上下文快照（含活跃任务）

/plan 模式的产物固定五段：问题分析、范围、步骤（有序）、风险与缓解、验证方式——最后等你说 execute / go 才动手。

三、四层规划模型

计划引擎对齐并增强了「参考实现」的计划功能，把计划拆成四层、逐层独立写入：

层 含义 回答的问题
goal 目标 任务最终达成什么
approach 方案 总体思路 / 技术选型
steps 步骤 具体执行步骤（每步带验证策略）
verification 验证 验收标准

分层的好处：目标与方案分离，避免「把实现细节写成目标」；步骤与验证绑定，避免「做完了却不知道怎么算通过」。

四、DAG 子计划与状态机

复杂任务拆成多个子计划，用 depends_on 声明依赖，构成有向无环图（DAG）：

[子计划A] ─┐
           ├─→ [子计划C] ─→ [子计划D]
[子计划B] ─┘
  • 拓扑调度：执行前校验依赖存在 + 无循环（DFS 检测）；
  • 状态机：Draft → Ready → Executing → Completed → Failed；
  • 级联失败：某子计划 Failed，依赖它的、仍处于 Ready 的子计划一并标记 Failed。
Draft ──run──▶ Ready ──▶ Executing ──▶ Completed
  │              │            │
  └──────────────┴────────────┴──▶ Failed ──▶（可回到 Draft / Ready）

五、plan 工具与 CLI

计划存储：.opencode/plans/plans.json（索引）+ <id>.md（详情）。对话中让 AI 调用 plan 工具，或用 CLI（不经过 LLM）：

plan init "重构认证模块"                      # 创建计划
plan write <id> goal "<目标>"                 # 四层逐层写入
plan write <id> approach "<方案>"
plan write <id> steps "<步骤>"
plan write <id> verification "<验收标准>"
plan sub "后端实现" --depends-on <id>         # 添加子计划 + 声明依赖
plan status                                   # 查看计划树与状态
plan run                                      # 校验（依赖存在 + 循环检测）并进入执行
plan update <id> Executing / Completed / Failed   # 推进状态（失败级联）

六、Todo：可追踪的结构化待办

todo 把「散落的诉求」固化为 markdown 文件，跨会话可查：

项 约定
存储 .opencode/todos/<MMDD-HHMM>-<slug>.md
frontmatter order（自增）/ title / type，activate 后追加 active: true
正文三节 ## 背景 / ## 目标 / ## 已知信息（goal 与 bug 同模板）
类型 goal（目标 / 功能 / 探索）或 bug（缺陷 / 异常 / 回归） 
todo add title="登录态刷新失败" type=bug    # 创建
todo list                                     # 按 order 升序列出
todo activate slug=<文件名或 slug>           # 激活（其余自动取消激活）

两种类型对应两条工作路径：goal 来自需求澄清（sk_goal），bug 来自调试（sk_debug）。无法判定时优先归为 goal。信息不足不编造，用 [TBD] — 待探索补充 占位，留待探索阶段补全。

七、双「会话」玩法：会话内待办 vs 跨会话 todo

定制版有两套待办语义，别混用：

内置 todowrite（会话内） todo 工具（跨会话）
范围 当前会话的临时清单 落盘 markdown，跨会话持久
用途 一次任务内的进度勾选 把工作项登记为可追踪锚点
触发 Agent 内部使用 todo 工具 / sk_todo 技能 / /todo
激活 无 activate 标记当前聚焦项

一句话：会话内的拆步用 todowrite，要跨会话跟进的用 todo。

八、task_manager：带依赖的任务流

task_manager 管理带依赖关系的任务（.opencode/tasks/tasks.json）：

操作 说明
create <标题> [--type goal\|bug] 创建任务，返回自增 ID（t1, t2…），初始 pending
update <id> --status <状态> 状态流转：pending → in_progress → completed（可加 blocked_by / blocks 依赖）
list / get <id> 列出 / 查看详情

两条硬约束：

  1. 同一时间只允许一个 in_progress 任务——强制聚焦，避免并行多任务失焦；
  2. 活跃任务自动注入上下文——lifecycle-hooks 把 in_progress 任务作为「工作锚点」注入每轮会话，让 Agent 始终感知在做什么（见 插件与扩展）。

九、落地清单

  1. 复杂任务先 /plan——不超过 3 步的任务不必规划，直接做；
  2. 四层写全——尤其别漏 verification，它是「做完」的唯一判据；
  3. 用子计划管理多条工作线——depends_on 表达真实依赖，别用执行顺序脑补；
  4. 跨会话工作项落 todo——用 sk_todo 补全三节，activate 当前聚焦项；
  5. 长任务挂 task_manager——blocked_by / blocks 表达依赖，活跃任务由 hooks 自动带回；
  6. 上下文紧张先 /compact_run——先压缩再执行，避免中途超预算（见 省 token 与上下文管理）。

相关工作流编排见 工作流；委派执行见 子代理与编排。
