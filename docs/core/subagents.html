首页 / 核心能力 / 子代理与编排

复杂任务不该由一个上下文窗口硬扛。子代理（subagent）把探索、实施、审查拆到独立会话里完成，只把结论回传主会话——既隔离了过程性 token，也让每类工作跑在合适的权限与模型档位上。本文对齐内部「参考实现」的多代理协作体验。

一、为什么用子代理

  • 上下文隔离：子代理在独立子会话运行，只有最终文本回传主会话，过程性 token 不污染主上下文（见 省 token 与上下文管理）；
  • 职责分明：只读探索不会被误写文件，审查代理不会「自己验证自己」；
  • 分档提效：探索、摘要这类轻活交给小模型档，重活再上主力模型（见 模型配置）；
  • 并行加速：无依赖的子任务可以同时委派，节省墙钟时间。

二、六大代理

新会话默认进入 coordinator 主代理（default_agent）。它自己不干活，负责拆解、委派与整合。另有 5 个子代理（mode: subagent）：

代理 职责 典型场景 上下文
explorer 只读探索（glob / grep / read） 代码搜索、事实发现、结构理解 独立子会话 + 小模型
executor 全权限实施（写代码、跑测试） 具体实现、多步骤任务 独立子会话
evaluator 独立审查（读 + 验证，禁写） 变更质量评估、回归检查 独立子会话（与 executor 隔离）
spawn 全权限派生 独立并行子任务 独立子会话
task-planning 只读规划（拆解 + 风险分析） 复杂任务先规划后实施 独立子会话

coordinator 负责「谁做」：拆解任务 → 按策略委派 → 评估置信度 → 整合验证 → 交付。它不重复子代理的工作，只做裁剪、合并与验证。

三、权限边界

子代理的能力范围由各自 frontmatter 里的 permission 声明，这是它与主代理最大的区别——用权限把角色钉死：

代理 允许 禁用
explorer read / glob / grep 其余全部（bash、write/edit、task、question、webfetch…）
evaluator read / glob / grep / bash / lsp write/edit、task、question
executor 全部核心工具 task、question、workflow-runner、eval-runner、cron、task-manager、background-task、env-store、git-worktree、new-asset、asset-manager
spawn 全部核心工具 同 executor
task-planning read / glob / grep / webfetch / question + 少量只读 git（status / log / diff / ls） write / edit / 其余 bash

全子代理统一禁用：task（不能再创建子代理）、question（不能问用户）、以及工作流 / 评估 / 定时 / 任务 / 密钥 / worktree / 资产等「管理类」工具——这些只归主代理。

放在 .opencode/agent/*.md 的权限规则经 init.sh 同步为全局 ~/.config/opencode/agent/*.md，opencode agent list 可验证；限制只作用于子代理，主代理不受影响。

四、编排四模式

选中 orchestrate 技能时按任务特征挑模式（详见 技能系统、skills/orchestrate/SKILL.md）：

条件 模式 流程
单步明确任务 Single 直接委派最合适的子代理
3+ 独立子任务、无文件冲突 Parallel 同时委派多个子代理，最后汇总
步骤间有依赖 Chain explore → build → evaluate，逐步摘要传递
需要质量验证、不允许回归 Refine build → evaluate → 修复 → evaluate，循环到通过 
                    ┌───────────────────────┐
                    │                       ▼
主代理 → [executor] → [evaluator] → 不通过? → [executor 修复] → [evaluator] → ✅

Refine 模式的三条纪律：设定最大迭代次数（推荐 3）、evaluator 反馈必须具体可执行、每轮只修指出的问题。复杂任务可混用：[Parallel 探索] → [Chain 实现] → [Refine 精炼]。

五、委派任务五要素

子代理是没有你对话记忆的独立会话，每次委派都必须自包含。coordinator 要求每个任务补齐五要素，缺一不可：

要素 说明
任务目标 一句话说清要拿到什么（以「任务目标」开头）
背景与已知信息 已核实的事实、相关文件路径、前置结论
范围与边界 覆盖什么、明确不做什么（如只读、不改文件）
验收标准 怎样算完成：证据要求、通过条件
期望产出 返回的结构与格式（报告、对比清单、表格等） 
# ❌ 模糊委派
task(subagent_type="executor", description="修复认证 bug", prompt="修复认证 bug")

# ✅ 充分上下文
task(subagent_type="executor", description="修复认证 bug",
  prompt="修复 internal/auth/handler.go:142 的 token 过期返回 500 问题。" +
       "要求使用现有 AuthError 类型，参考 handler.go:98 的错误处理模式。" +
       "验证：go test ./internal/auth/... 全绿。")

六、task 工具实现要点

子代理由内置 task 工具拉起，几个关键机制：

机制 行为
独立子会话 每次委派创建一个 parentID 指向当前会话的新会话，标题形如 描述 (@explorer subagent)
子代理默认小模型 agent frontmatter 写 model: small → 解析为 small_model；未配置时回退父模型（explorer 已默认挂载）
并发上限 subagent_max_concurrency（默认 4，范围 1-8），进程级 FIFO 信号量，跨会话统一限流，避免并发风暴
嵌套深度 subagent_depth（默认 1），达到上限即拒绝再往下委派
会话续接 传 task_id 可续接同一子会话，而不是新建
后台子代理 background: true 异步运行、完成自动通知；需 OPENCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS=true 开启

并发是进程级而非会话级：同一进程内所有 task 调用共享一个信号量，保证全局子代理数量不超限。

七、与「参考实现」对齐的要点

参考实现语义 定制版落点
explorer 只读、最快最省 explorer 仅 read/glob/grep + model: small，无 bash
子代理独立上下文、只回收结论 task 新建子会话，仅回传最终文本
并行受控，防止并发风暴 subagent_max_concurrency 进程级信号量（1-8）
探索 → 实施 → 独立审查 explorer / executor / evaluator 三档 + 权限隔离
编排模式可复用 orchestrate 技能固化 Single / Parallel / Chain / Refine

八、落地清单

  1. 先探索再动手——不确定代码结构时，先花 1 轮 explorer 拿到「地图」，再决定改哪里；
  2. 并行前先查冲突——两个 executor 同时改同一个文件 = 灾难，独立边界才并行；
  3. 摘要而非全文——向下游传递上一步的关键发现，不要把完整输出塞给下一个子代理；
  4. 审查必须独立——evaluator 不复用 executor 的上下文做自我确认；
  5. 失败有降级——explorer 未找到信息最多重试 2 次；evaluator 连续 3 轮不通过即停止并上报（见 快速定位问题）；
  6. 低置信度不采信——子代理返回后先评估置信度，存疑就补查或换角度复核。

省 token 的视角：委派本身就是把「过程」移出主上下文。相关机制见 省 token 与上下文管理，工具入口见 自定义工具。
