首页 / 核心能力 / 省 token 与上下文管理

省 token 不只是省钱：它同时换来更大的有效上下文（同样预算装更多信息）与更快的响应（每轮输入更短）。本文先分析「参考实现」的省 token 设计，再给出 opencode 定制版的对应机制与落地清单。

一、先看清成本模型

每一轮请求发送给模型的内容大致是：

系统提示（AGENTS.md / 技能列表 / 工具描述 / 环境信息）
  + 对话历史（逐轮累积）
  + 工具输出（读文件、命令返回等）
  + 本轮生成（含思考）

要点：

  • 历史与工具输出会随对话累积——不清理就是持续付费；
  • 系统提示是每轮固定成本——文件越臃肿，每轮都贵；
  • 工具输出最容易失控——一次 cat 大文件顶上几百轮对话。

所以省 token 的三条主线：控输入（每轮携带什么）、控输出（生成与工具结果多大）、控频率（不做无效轮次）。

二、参考实现的省 token 设计（对照分析）

# 机制 原理 效果
1 模型分档 轻活（探索、摘要）用 flash 档，重活用 pro 档，视觉单独回退 单价差可达数倍；轻量任务近乎免费额度
2 子代理独立上下文 探索/执行在独立会话窗口完成，只把结论回传主会话 过程性 token 不进入主上下文，主会话保持精简
3 explorer 快扫 只读工具 + 「了解结构不深挖细节」的提示词纪律 探索阶段用最小代价拿到地图
4 后台任务输出落盘 长命令输出写文件，完成后只发通知 大输出不占对话上下文
5 工具输出截断/落盘 超限结果存文件 + 头尾预览 单条工具结果有硬上限
6 上下文压缩 预算触发自动压缩；/compact 手动清理；保留近期原文 长会话可持续
7 技能按需加载 系统提示只放「名称 + 描述」，正文用时才注入 技能再多，固定成本不变
8 上下文文件精炼 AGENTS.md「只写 Agent 需要知道的知识和约束」 压低每轮固定成本
9 持久锚点 计划 / Todo / 场景 reference 落盘，跨会话引用 避免重复探索与复述
10 可度量 用量统计、评估里的 cost / latency 门禁 优化有基线，防止回退

观察：这些机制里，对成本影响最大的是「分档模型」与「子代理隔离」——即把工作放到正确的模型和正确的上下文窗口里，而不是在提示词上抠字眼。

三、opencode 定制版的对应机制

能力 opencode 实现 开关/落点
小模型 small_model 配置；标题生成等轻任务自动使用 opencode.json → small_model
子代理默认小模型 agent frontmatter 写 model: small → 解析为 small_model（解析不到回退父模型） .opencode/agent/explorer.md 已默认挂载
子代理隔离上下文 子代理在独立子会话运行，仅把最终文本回传主会话 内置 task 工具（自动）
子代理并发上限 subagent_max_concurrency（默认 4，范围 1-8）防止并发风暴 opencode.json
工具输出限制 tool_output.max_lines / max_bytes，超限写文件 + 预览 opencode.json（模板默认 200 行 / 8KB）
自动压缩 以模型 limit.context 为预算触发；缺 limit 的私有模型由 init.sh 注入 200k/32k 预算 init.sh（自动注入）+ compaction
压缩策略 auto / tail_turns / preserve_recent_tokens / reserved / prune opencode.json → compaction
后台任务 background-task 工具：输出落盘 .opencode/tasks/*.log，完成记录退出码并通知 对话中让 Agent 后台执行即可
技能轻列表 系统提示只列技能名与描述，正文经 skill 工具按需加载 保持技能 description 简短
用量统计 opencode stats、会话上下文指标（token/上限占比） CLI / TUI
提示词缓存 Context Epoch 机制保持系统提示基线逐字稳定，命中 provider 缓存（缓存读约 0.1x 价） 内置；避免会话中途频繁改 AGENTS.md

四、落地清单

4.1 配置（照抄即可）

// ~/.config/opencode/opencode.json
{
  "small_model": "<轻量模型，如你的 flash 档>",
  "compaction": {
    "auto": true,
    "tail_turns": 4,
    "preserve_recent_tokens": 8192,
    "reserved": 16384
  },
  "tool_output": { "max_lines": 200, "max_bytes": 8192 }
}

私有模型缺 limit 时不会触发自动压缩。./init.sh 会为私有模型自动注入 context=200000 / output=32768 的有效预算；官方模型由目录自动解析，无需配置。

4.2 使用习惯

  1. 先探索，后动手——让 explorer 子代理先给「地图」，再决定改哪里；
  2. 精准检索——grep 定位行号后按 offset/limit 读片段，禁止整文件倾倒；
  3. 委派重活给子代理——多文件调研、批量验证都会污染主上下文；
  4. 长命令进后台——构建/全量测试用后台任务，输出落盘；
  5. 长会话及时压缩——/compact，或依赖自动压缩；换任务尽量 /new；
  6. 上下文文件保持精炼——AGENTS.md 只写「无法从代码推断」的约定与命令；
  7. 模型分对档——探索/摘要用 small_model 档，重活再上主力模型。

4.3 度量

  • 会话后 opencode stats 看 token/成本趋势；
  • 评估场景加 cost_under / latency_under / turns_under 门禁（eval-runner 已支持），防止「答对但烧钱」；
  • 改动提示词/配置前后跑同一评估场景对比分数与成本。

五、常见误区

误区 后果 正解
整段读大文件/大日志 单次吞掉巨额预算 先 grep 定位，再局部读
同一命令反复重试 重复输出入上下文 失败先诊断（见快速定位问题），3 次即停并上报
长会话不压缩 每轮都在重发旧历史 /compact 或自动压缩；任务切换开新会话
让主会话干探索的活 过程 token 全部留在主上下文 委派 explorer；只回收结论
AGENTS.md 变「项目百科」 每轮固定成本水涨船高 只写必要知识与约束，细节放文档
所有任务都用旗舰模型 单价 × 调用量双高 轻活走小模型/快档，重活再上强模型
