首页 / 应用实践 / 编排思考逻辑（工作法）

本文沉淀一套可复用的协作工作法：把模糊的大任务变成「对齐 → 取证 → 拆解 → 派发 → 验证收敛」的可靠流程。它来自多代理实际编排实践（并行子代理 + 独立验证 + 分批交付），可直接迁移到任何复杂任务。

一、总原则

  1. 先对齐再动手——意图明确度分档：High 直接做；Medium 复述确认；Low 必须用结构化选项提问（一屏问完、标注推荐项）。
  2. 证据优先——结论分级 [Confirmed] / [Inferred] / [Uncertain]；先读代码、查文档、跑命令，多源交叉后再下判断。
  3. 能并行不串行、能委派不亲干——独立子任务并行派发；探索/实现的过程性开销放进子代理的独立上下文。
  4. 先骨架后批量——先用最小骨架验证通道（构建脚本、接口、流程），再批量生产内容。
  5. 产出必须独立验证——子代理报告「完成」不等于完成；编排者要亲手复跑关键验证。

二、五步循环

1. 对齐（Clarify）

  • 先复述理解，再用选项化提问补齐缺口；把「推荐做法」写进选项说明，降低用户决策成本。
  • 典型四问：范围 / 交付物 / 边界（哪些不做）/ 交付方式。
  • 例：本仓库实践中，动手前先问「补齐范围（文档/配置层/含源码）、省 token 交付、文档范围、开发方式」四问。

2. 取证（Recon）

  • 先读再断：读代码、拉取外部文档、核对 git 历史与既有资料。
  • 把「用户说的」也当作可验证假设：先核对再行动（例如用户描述的功能可能与实现不符，早发现早修正）。
  • 例：完整抓取知识库全量页面（38 页）后，先与仓库既有归档对照，找出「文档声称有、代码没有」的差距。

3. 拆解（Decompose）

  • 粒度：3+ 步或独立交付物才拆；每个任务一个明确交付物 + 可执行验收。
  • 先列任务表，再判断依赖：独立 → 并行；有依赖 → 串行/链式。
  • 任务说明书五要素：目标 / 范围（文件白名单，避免并行冲突）/ 约束 / 验证要求 / 输出格式。

4. 派发（Dispatch）

  • 并行优先：互不重叠的文件域一次派发多个 executor；串行只用于真依赖。
  • 共享背景一次给全：仓库背景、命名约定、禁止事项统一放在共享语境里，不要让每个子任务重复描述。
  • 给证据路径：关键接缝给到「文件:行号」级别（如 task.ts:181），减少子代理盲目搜索。
  • 骨架先行：先搭最小可用骨架（如文档站的构建脚本 + 3 个范例页），验证通道后再批量生产。

5. 验证收敛（Verify & Integrate）

  • 独立验证：typecheck / 单测 / 冒烟测试在编排者这一层重跑，不轻信子代理的自述。
  • 要求子代理报告「拿不准的点」：本实践中 4 个子代理各自列出「与源文档不符」清单（数量漂移、机制不存在等），直接转化为后续修复项——这是高价值的副产品。
  • 差异处理：逐条决定「修实现」还是「修文档」，并记录在案。
  • 分批提交：按特性拆分 commit，每个 commit 自洽可回滚；消息写清「做了什么/为什么/怎么验证」。

三、失败与卡壳：不深入错误路径

在可疑但不正确的路径上「再挖深一点」是最贵的操作——烧时间、烧预算，还制造「快要找到了」的错觉。

  • 失败即停：同一操作连续失败 3 次，停止重试并上报阻塞（Fail forward）。
  • 卡壳协议（与快速定位问题同源）：连续 2+ 轮无新证据、信心停滞、假设无法证实 → 停止，汇总「已排除清单 + 具体 UNKNOWN」，交给最廉价的信源（人）判断。
  • 先穷举、后深入：用低成本实验（读日志、二分、最小复现）排除整类可能，而不是押注一条路径。

四、省 token 的编排

与省 token 与上下文管理呼应，编排层面同样有杠杆：

做法 效果
独立调用批量并发（一条消息多个工具调用） 减少往返轮次
探索/实现委派给子代理 过程 token 不进入主上下文
大输出落盘、按需读取 控制单条结果体积
grep 定位 + 偏移读 避免整文件倾倒
共享背景一次给全 避免每任务重复描述

五、一页检查清单

动手前 - [ ] 目标 / 范围 / 验收 / 约束清楚吗？Low 信心项问了吗？ - [ ] 关键事实核对了吗（代码、文档、历史）？

派发前 - [ ] 文件域不重叠吗？验收标准可执行吗？ - [ ] 共享背景、证据路径给全了吗？禁止事项写了吗？

集成前 - [ ] 关键验证独立跑过了吗？ - [ ] 子代理「拿不准的点」处理了吗？ - [ ] 提交粒度与消息符合仓库惯例吗？
